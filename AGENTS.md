# AGENTS.md

## File organization

- Organize files by feature or responsibility. Reuse existing directories before creating new ones; keep related components, helpers, and unit tests close to the feature they support.
- Move code to shared locations only when it is actually reused across features, except for frontend components as described below. Avoid catch-all directories mixing unrelated responsibilities and folders wrapping a single file without a concrete reason.
- Preserve framework entrypoints, routing conventions, configuration locations, and the configured migration structure.
- Follow each app's existing import conventions and prefer direct imports over unnecessary barrel exports. When moving files, update all affected imports, configuration, and documentation.

## Desktop (`apps/desktop`)

- Electron shell, plain ESM (`.mjs`) with no build step; the sandboxed preload is `src/preload.cjs`. Keep the main process small: window, Next.js child process, workspace folder, `safeStorage` secret, and the agent bridge.
- Keep local speech-to-text in `src/whisper.mjs` / `src/whisper-worker.mjs` (child process; `onnxruntime-node` must stay asar-unpacked and other platforms' binaries are excluded per platform in `package.json`). Keep agent CLI logic in `src/agents.mjs` with `bun:test` tests beside it. The renderer may only start presets by id; never accept a command line from it, validate IPC senders with `isTrustedSender`, and do not pass `LOMRA_*` variables to the agent.
- Packaging is configured in `package.json` (`electron-builder`): `bun run pack` (unpacked) and `bun run dist` (installer). The Next.js `standalone` output ships in `resources/web`; `scripts/after-pack.cjs` copies its `node_modules`, and `@lydell/node-pty` must stay asar-unpacked. Tag builds run `scripts/check-signature.ps1` (tested beside it; see `docs/code-signing.md`).
- Version & update checks live in `src/updates.mjs` (tested in `src/updates.test.mjs`) and expose `app:version`, `app:checkUpdate`, `app:openRelease`, `app:installUpdate`, `app:cancelUpdate`, and `app:updateProgress` IPC (`lomra.app` in `lib/desktop.ts`, shared client state in `hooks/use-app-update.ts`, shown in `components/update-toast.tsx` and `components/app-version-footer.tsx`); releases are read from GitHub Releases (`Nxdus/lomra-app`), surfaced via a persistent update toast on desktop start, and opened externally only when `isReleaseUrl` allows them. In-app install is Windows-only for packaged builds using the last cached check result (the renderer passes no URL or path): the installer is streamed to temp `lomra-update/` via `.part`, verified by size and SHA-256 against the GitHub asset digest, and launched silently with NSIS `/S --updated --force-run` before quitting.
- Verify changes with `bun test` and a launch with `LOMRA_SMOKE=1` (it loads the app, checks the agent bridge and quits).

## Data

- The app is local-first: no accounts, database or cloud storage. `/api/storage` (`apps/frontend/app/api/storage/`) reads and writes the workspace folder (`LOMRA_DATA_DIR`, default `~/Documents/Lomra`) through `apps/frontend/lib/local-store/`: `canvas/`, `chats/`, `settings/` and `keys/` as JSON (keys AES-GCM encrypted) and media in `files/`.
- Saved state is validated in `lib/local-store/validation.ts`; update it together with any change to the saved canvas, chat or settings shapes. Keep IDs matching `^[w-]{1,128}$` so they are safe file names.
- Local LLMs run through Ollama, no API key. The server is the `ollama-url` setting (Settings → Local models; may be another computer), else `OLLAMA_URL`, else `http://127.0.0.1:11434`; the desktop app finds the CLI and starts `ollama serve` only for a local server (`apps/desktop/src/ollama.mjs`). `app/api/ollama/` lists, installs (streamed pull) and removes models; chat and routing go through `app/api/providers` with provider `ollama` and model IDs `ollama/<name>`. Only models that report the `tools` capability are offered, because chat is routed by tool calls. Install UI: `components/ollama-settings.tsx` (Settings → Local models).
- Image, 3D and ffmpeg downloads go through `apps/desktop/src/download.mjs` (`bun:test` beside it, with a real HTTP server): `downloadFile` keeps an unfinished file as `<file>.<sha256 prefix>.part` and continues it with a Range request; only a file whose whole SHA-256 matches reaches its final path. `createDownloadQueue` runs the image and the 3D models one after another each; `status()` lists `queued` models and the `partial` bytes of paused ones. `remove()` also deletes an unfinished download, and keeps the engine while anything is queued, unfinished or generating.
- Local image generation runs stable-diffusion.cpp's `sd-cli` from the desktop app (`apps/desktop/src/sd.mjs`, profile definitions in `src/sd-profiles.mjs`, pinned engine build and checkpoints with SHA-256 in `src/sd-models.mjs`, `bun:test` beside it). Files go to userData `stable-diffusion/`; downloads start only after the user agrees in `components/sd-settings.tsx` (Settings → Local models). The renderer reaches it over the `sd:*` IPC (`lomra.sd`, typed in `lib/desktop.ts`) with a model id, prompts, an aspect ratio, bounded numbers (seed, steps, CFG, strength) and picture/mask data URLs only, all checked against the model's profile ranges and capabilities in `src/sd-input.mjs`, never a path or command line. Besides the built-in models, any single-file `.safetensors`/`.gguf` checkpoint on Hugging Face can be added (`components/sd-huggingface.tsx` searches as the user types, `components/sd-download-dialog.tsx` confirms; `src/sd-header.mjs` reads the type, and whether it is an inpainting model, from the file's first bytes, remote or installed, and refuses anything but whole SD 1.x/2.x/SDXL checkpoints; few-step models are guessed from the name and the user can correct it before download or switch to another compatible profile after installation via `sd:setProfile`; a file that is a built-in model is kept as that model; huggingface.co `owner/name` repos and checkpoint subfolders, verified against the hash Hugging Face lists, saved in `custom/` with a record (written before the download, so it can resume after a restart), run with the settings of the chosen profile). Local checkpoints can be selected or scanned through native dialogs and used in place (`src/sd-local.mjs`); only main-process userData records contain the absolute paths, and removal forgets the record. Picture models are `sd/<id>` and are generated in `components/prompt/generation.ts`: capabilities come from `lib/picture-capabilities.ts` (from text, or from exactly one selected picture for image-to-image, or inside the Picture Editor's brushed area where white in the mask is redrawn). `components/prompt/sd-image.ts` prepares pictures and undoes the engine's rounding to 64 px. Per-model settings are the `sd-settings` setting (`lib/sd-settings.ts`, `components/prompt/sd-settings-popover.tsx`); what was used is stored as `provenance.sd`. Storyboard shots use no references when the model does not support them, and say so.
- Local image-to-3D runs from the desktop app (`apps/desktop/src/local3d.mjs`, pins and the model list in `src/local3d-models.mjs`, worker scripts in `src/local3d-worker/`, `bun:test` beside it). After the user agrees in `components/local3d-settings.tsx` (Settings → Local models; NVIDIA GPU with 6 GB+, Windows x64) it installs one shared environment into userData `local3d/` (the uv installer, a private Python 3.10, CUDA PyTorch, pinned libraries and the Hunyuan3D `hy3dgen` code), then the weights of each model the user picks (Hunyuan3D 2 Mini, Hunyuan3D 2, TripoSR; shape only, TripoSR adds vertex colors). Everything is SHA-256 checked or an exact version, and `torchmcubes` is replaced by a scikit-image shim so nothing has to be compiled. Each run starts `worker.py` as a fresh process with `HF_HUB_OFFLINE=1`; the renderer reaches it over the `local3d:*` IPC (`lomra.local3d`, typed in `lib/desktop.ts`) with a model id and one picture, never a path. 3D models are `local3d/<id>` and are generated in `components/prompt/generation.ts`; they need no Fal key. To add a model, add an entry to `local3dModels` (and a worker `kind` if it needs new code); bump `local3dVersion` when an engine pin changes.
- Local image and 3D runs share one queue (`apps/desktop/src/gpu-queue.mjs`, created in `main.mjs`): one at a time, and before each turn `src/ollama-unload.mjs` unloads the models of an Ollama on this computer (loopback only, best effort). A task must settle only when its process is gone (`whenGone`); waiting runs report `waiting` in `sd:progress` / `local3d:progress`.
- Canvas details and Compare use picture-generation provenance for setup reuse, and local SD results without a brush mask can generate four variations. The per-run settings in `components/prompt/generation.ts` use the same profile capabilities as saved settings. Picture tools record their model in provenance for comparison.
- Local background removal and upscaling (`2x`, `4x`) run pure CPU ONNX models through `onnxruntime-node` and `sharp` in a child process (`apps/desktop/src/picture-ai.mjs`, `src/picture-ai-worker.mjs`, pinned models in `src/picture-ai-models.mjs`, `bun:test` beside it), never blocking `gpuQueue` or unloading Ollama. Downloads start only after the user agrees (`components/picture-ai-settings.tsx`, or the prompt/editor download dialog); the renderer reaches it over `picture:*` IPC (`lomra.picture`, typed in `lib/desktop.ts`, validated via `sd-input.mjs` `picture`), and desktop routing prefers local models (`local-picture/<id>`) without silent Fal fallback.
- The storyboard belongs to the canvas, not the open chat: `FloatingPrompt` keeps one storyboard per canvas (with its reference pictures and `boardOwner`, the chat that stores it as `chat.storyboard`), so it stays visible whichever chat is open. Opening a chat that holds one shows that one; a new `/storyboard` replaces the one on the canvas (the old stays in its chat). Only the owner chat's panel and prompt work on the story text; edits made from the canvas are saved into the owner chat. The finished video is a normal canvas item remembered as `storyboard.videoItemId`; the last shot's arrow follows it.
- The storyboard's "Make video" button makes one clip per shot with the selected video model (the shot picture is the first frame; `components/prompt/floating-prompt.tsx` `makeStoryboardVideo`, clips are workspace files kept as `videoId` on each shot) and joins them into one MP4 on the canvas with ffmpeg from the desktop app (`apps/desktop/src/ffmpeg.mjs`, pinned build and SHA-256 in `src/ffmpeg-models.mjs`, `bun:test` beside it). It is downloaded into userData `ffmpeg/` only after the user agrees in the Make video dialog. The renderer reaches it over the `video:*` IPC (`lomra.video`, typed in `lib/desktop.ts`) with clip bytes, lengths and an aspect ratio only, never a path or command line. Each clip is scaled to one size, cut or held (last frame) to its shot's seconds and given silence if it has no sound; the output is H.264 (`libopenh264`, because the LGPL build has no x264) and AAC. Video requests accept one first-frame picture, a duration and an aspect ratio on OpenRouter (`app/api/providers/route.ts`); Google's Veo API still takes text only, so it cannot be used for storyboard clips. BtbN prunes old autobuild tags, so bump `ffmpegRelease`, `asset`, `sha256` and `bytes` together when the pin disappears.
- Voice input calls a Whisper service (`WHISPER_URL`) directly from `app/api/transcriptions`. The desktop app starts a bundled one (`apps/desktop/src/whisper-worker.mjs`, transformers.js, models listed in `src/speech-models.mjs`, cached in userData and downloaded only after the user agrees in a native dialog; the mic button's right-click menu in `components/prompt/speech-menu.tsx` manages them); without it point `WHISPER_URL` at a Whisper ASR Webservice-compatible service. The browser converts recordings to 16 kHz WAV first (`components/prompt/wav.ts`).

## Frontend (`apps/frontend`)

### File organization

- Keep Next.js App Router routes, layouts, and route handlers under `app/`, preserving special filenames such as `page.tsx` and `layout.tsx`. Colocate route-specific helpers, hooks, and tests with the route.
- Put standalone UI components under the existing `components/`, even when currently used by only one route. Keep UI primitives in `components/ui/` and feature or navigation components outside `components/ui/`. Group by feature only when useful; do not create a folder just to wrap one component.
- Put genuinely shared hooks in `hooks/` (already configured in `components.json`) only when needed. Keep shared non-UI utilities in the existing `lib/`, including `lib/utils.ts`; keep feature-only helpers with their feature.
- Keep saved-data and workspace file logic server-side in `lib/local-store/`; client code reaches it only through `lib/storage.ts`. Bridge types for the Electron preload live in `lib/desktop.ts`.
- Follow the existing `@/*` alias rooted at `apps/frontend` and the aliases in `components.json`; use local relative imports where appropriate. Preserve app-root Next.js, TypeScript, ESLint, and shadcn configuration and `app/globals.css`.

### UI components

- Prefer shadcn/ui components before building UI from scratch, including forms, inputs, buttons, dialogs, and tables.
- Check existing project components first. If a suitable shadcn/ui component is missing, add it using the shadcn CLI and compose or customize it to fit the app.
- Build a custom component only when existing project components and shadcn/ui cannot reasonably meet the requirement. Keep styling consistent with the project's theme and preserve accessibility.
